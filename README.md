# Backend

Backend проекта для сопровождения Git workflow и накопления контекста
разработки.

## Архитектура и работа системы

Пользователь создаёт рабочие области (`workspace`), в них ветки (`branch`), а в
ветки добавляет изменения (`change`) с текстом diff. Для каждого изменения
AI-сервис асинхронно формирует результат анализа (`analysis_result`) и в случае
успешного анализа асинхронно формирует коммит (`commit`). Генерация PR пока не
реализована.

### HTTP-сервер и фоновые задачи

Backend работает как один процесс на Go, в котором HTTP-сервер на Gin и
фоновые задачи выполняются в отдельных горутинах. Данные хранятся в БД
PostgreSQL, обмен с отдельным AI-сервисом идёт через брокер сообщений RabbitMQ.
AI-сервис получает все входные данные в сообщении и не обращается к БД.

Фоновые задачи:

- **Outbox worker** раз в секунду выбирает до 10 команд, готовых к отправке,
  и публикует их в RabbitMQ с ограниченными повторами; раз в час удаляет
  старые записи опубликованных команд и команд с исчерпанным лимитом попыток.
  Запись текущей команды сохраняется, пока коммит в `pending`.
- **Consumer'ы сообщений** читают результаты анализа и генерации коммитов из
  RabbitMQ и сохраняют их в БД.
- **Worker'ы таймаутов** каждые 30 секунд переводят просроченные анализы и
  коммиты в `failed`.
- **Очистка refresh-токенов** раз в час удаляет истёкшие refresh-токены из БД.

Фоновые задачи используют общий контекст отмены. При остановке приложение
завершает их работу, останавливает HTTP-сервер и закрывает соединения с БД и
брокером.

### Создание change, analysis_result и commit

Доступ к данным требует JWT access-токен. Все ресурсы доступны только владельцу
workspace; совместного доступа и ролей нет. Чужие ресурсы возвращают `404`.

При `POST /branches/{branch_id}/changes` сервер:

1. Проверяет `raw_diff`: строка не должна быть пустой или состоять только из
   пробелов, формат diff не проверяется. Всё HTTP-тело ограничено 1 МиБ, включая
   JSON и экранирование; превышение возвращает `413`.
2. В транзакции блокирует строку ветки (`FOR UPDATE`) и проверяет её статус. В
   `closed` добавлять изменения нельзя (`409`). Блокировка последовательно
   обрабатывает параллельные создания в одной ветке; номер изменения вычисляется
   как `MAX(sequence_number) + 1`. Повторное открытие ветки сохраняет историю и
   продолжает нумерацию.
3. Создаёт изменение, анализ и коммит в статусе `pending`, добавляет
   `analysis.request` в `outbox` и фиксирует транзакцию. Ограничение
   `UNIQUE (change_id)` допускает по одной записи анализа и коммита на
   изменение. Полный `raw_diff` хранится в изменении и в payload команды
   вместе с `analysis_id`.
4. Возвращает `202 Accepted`. Клиент получает результат анализа и коммит
   опросом `GET /changes/{change_id}`.

### Публикация команд и RabbitMQ

Outbox worker раз в секунду читает из таблицы `outbox` до 10 неопубликованных
команд без `failed_at`, у которых наступил `next_attempt_at`, и последовательно
отправляет их в exchange `generation.commands`. Поле `message_type` задаёт
routing key и AMQP `type`. Команда `analysis.request` попадает в очередь
`generation.analysis.requests`, откуда её получает AI-сервис. Результат
`analysis.result` он публикует в exchange `generation.results`, который
направляет его в очередь `generation.analysis.results` для backend.

Backend объявляет топологию при подключении: durable direct exchanges,
quorum-очереди с `x-delivery-limit: 5` и отдельной DLQ для каждой очереди через
`generation.dlx`. Сообщения передаются как persistent JSON.

Поле `outbox.published_at` хранит время публикации команды и заполняется только
после подтверждения от брокера (publisher confirm). Возврат сообщения брокером
(`basic.return`, публикация с `mandatory`) считается ошибкой.

При ошибке публикации backend сохраняет её причину и откладывает повторную
отправку команды. Всего допускается 5 попыток с задержками 5, 10, 20 и 40
секунд. После пятой ошибки отправка прекращается. Когда истекает таймаут,
backend переводит статус генерации в `failed`. Записи опубликованных команд и
команд с исчерпанным лимитом попыток удаляются по истечении срока хранения
`OUTBOX_RETENTION` в `.env` (по умолчанию 7 дней).

Доставка работает по принципу **at-least-once**: сбой между публикацией и
записью `published_at` допускает повторную отправку. Каждый экземпляр backend
запускает свой worker без координации, поэтому несколько экземпляров тоже могут
отправить одну команду.

При разрыве соединения с брокером оно восстанавливается при очередной публикации
или потреблении с увеличением задержки между попытками от 1 до 30 секунд.

### Получение и обработка результатов

ID записи outbox передаётся в поле `message_id` сообщения и сохраняется при
повторных публикациях. Тот же ID хранится в поле `message_id` соответствующего
анализа или коммита. AI-сервис возвращает его в `correlation_id` результата.

Каждый consumer обрабатывает сообщения последовательно с manual ack и
`prefetch=10`. Результат применяется, только если анализ или коммит существует,
находится в `pending` и ID команды совпадает. Остальные валидные результаты
подтверждаются (`ack`) и игнорируются. Наличие записи в outbox для этого
не требуется.

У анализа два конечных состояния: `pending → done | failed`:

- Для `done` нужен валидный JSON в `structured_changes`, отличный от `null`.
  Структура и содержимое не проверяются. Поле `error` должно отсутствовать.
  Backend сохраняет результат и добавляет `commit.request` с
  `structured_changes` в outbox в одной транзакции.
- Для `failed` нужны `error.code` и `error.message`, содержащие хотя бы один
  непробельный символ. Поле `structured_changes` должно отсутствовать.
  Причина остаётся в логах, а ожидающий коммит переходит в `failed` вместе с
  анализом.

Результат `commit.result` приходит через очередь `generation.commit.results`.
Как и анализ, коммит переходит из `pending` в `done` или `failed`.
При `done` backend сохраняет `type`, `scope` и `message`. При `failed`
причина записывается в лог, а поля сообщения коммита остаются `NULL`.

Невалидное сообщение логируется и сразу направляется в DLQ через `nack`
с `requeue=false`. Статус анализа или коммита остаётся прежним.
Инфраструктурная ошибка обработки приводит к `nack` с `requeue=true`; после
лимита доставок сообщение уходит в DLQ для ручного разбора.

Чтобы анализы не застревали в статусе `pending`, worker таймаутов переводит их в
`failed` по истечении таймаута. Проверка выполняется каждые 30 секунд.
Таймаут задаётся переменной окружения `GENERATION_TIMEOUT` в `.env`
(по умолчанию 5 минут) и отсчитывается от создания анализа, включая ожидание
публикации и генерацию. При таймауте анализа ожидающий коммит тоже переходит
в `failed`. Для коммита таймаут отсчитывается от публикации текущей
команды `commit.request`, а для ещё не опубликованной команды - от её записи
в outbox. Если результат приходит после перехода в `failed`, backend
игнорирует его.

Удаление ветки или workspace каскадно удаляет изменения, анализы и коммиты. Ни удаление,
ни таймаут не отменяют команды в outbox и RabbitMQ: генерация может выполниться,
но её результат будет проигнорирован.

## Разработка

### Локальный запуск

Скопируйте файл окружения:
```bash
cp .env.local.example .env
```

Запустите сервер:
```bash
go run ./cmd/server
```

### Запуск через Docker Compose

Скопируйте файл окружения:
```bash
cp .env.docker.example .env
```

Запустите сервисы:
```bash
docker compose up --build
```

### Заглушка AI-сервиса

`cmd/ai-stub` заменяет AI-сервис при локальной разработке. Получает
`analysis.request` и `commit.request` из RabbitMQ и отправляет соответствующие
`analysis.result` и `commit.result` со статусом `done` или `failed`.
Заглушка подключается к RabbitMQ на `localhost`. Порт и учётные данные
берутся из окружения и `.env`. Запустите в отдельном терминале:
```bash
go run ./cmd/ai-stub
```

Флаги:
- `-result`: режим результата (`done`, `failed` или `random`), по умолчанию
  `random`.
- `-success-rate`: вероятность успеха в режиме `random`, по умолчанию `0.8`.
- `-delay`: задержка перед отправкой результата, по умолчанию `1s`.
- `-seed`: начальное значение генератора случайных чисел для воспроизводимых
  результатов, по умолчанию используется текущее время.

### Доступ

Сервер: http://localhost:8080 \
Swagger UI: http://localhost:8080/swagger/index.html

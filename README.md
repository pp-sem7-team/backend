# Backend

Backend проекта для сопровождения Git workflow и накопления контекста разработки.

## Архитектура и работа системы

Пользователь создаёт рабочие области (`workspace`), в них ветки (`branch`), а в ветки добавляет изменения (`change`) с текстом diff.
Для каждого изменения AI-сервис асинхронно формирует результат анализа (`analysis_result`) и в случае успешного анализа асинхронно генерирует сообщение для коммита (`commit`).
Когда анализ всех изменений ветки завершился успешно, пользователь может запустить генерацию заголовка и описания PR (`pull_request`).

### HTTP-сервер и фоновые задачи

Backend работает как один процесс на Go, в котором HTTP-сервер на Gin и фоновые задачи выполняются в отдельных горутинах.
Данные хранятся в БД PostgreSQL, обмен с отдельным AI-сервисом идёт через брокер сообщений RabbitMQ.
AI-сервис получает все входные данные в сообщении и не обращается к БД.

Фоновые задачи:

- **Outbox worker** раз в секунду выбирает до 10 команд, готовых к отправке, и публикует их в RabbitMQ с ограниченными повторами; раз в час удаляет старые записи опубликованных команд и команд с исчерпанным лимитом попыток.
  Запись текущей команды сохраняется, пока коммит в `pending`.
- **Consumer'ы сообщений** читают из RabbitMQ сообщения с результатами анализа, коммитами и PR и сохраняют данные в БД.
- **Worker'ы таймаутов** каждые 30 секунд переводят просроченные результаты анализа, коммиты и PR в `failed`.
- **Очистка refresh-токенов** раз в час удаляет истёкшие refresh-токены из БД.

Фоновые задачи используют общий контекст отмены.
При остановке приложение завершает их работу, останавливает HTTP-сервер и закрывает соединения с БД и брокером.

### Создание change, analysis_result и commit

Доступ к данным требует JWT access-токен.
Все ресурсы доступны только владельцу workspace; совместного доступа и ролей нет.
Чужие ресурсы возвращают `404`.

При `POST /branches/{branch_id}/changes` сервер:

1. Проверяет `raw_diff`: строка не должна быть пустой или состоять только из пробелов, формат diff не проверяется.
   Всё HTTP-тело ограничено 1 МиБ, включая JSON и экранирование; превышение возвращает `413`.
2. В транзакции блокирует строку ветки (`FOR UPDATE`) и проверяет её статус.
   В `closed` добавлять изменения нельзя (`409`).
   Блокировка последовательно обрабатывает параллельные создания в одной ветке; номер изменения вычисляется как `MAX(sequence_number) + 1`.
   Повторное открытие ветки сохраняет историю и продолжает нумерацию.
3. Создаёт изменение, результат анализа и коммит.
   Результат анализа и коммит получают статус `pending`.
   Сервер добавляет `analysis.request` в `outbox` и фиксирует транзакцию.
   Ограничение `UNIQUE (change_id)` допускает один результат анализа и один коммит на изменение.
   Полный `raw_diff` хранится в изменении и в payload команды вместе с `analysis_id`.
4. Возвращает `202 Accepted`.
   Клиент получает результат анализа и коммит опросом `GET /changes/{change_id}`.

### Публикация команд в RabbitMQ

Outbox worker раз в секунду читает из таблицы `outbox` до 10 неопубликованных команд без `failed_at`, у которых наступил `next_attempt_at`, и последовательно отправляет их в exchange `generation.commands`.
Поле `message_type` задаёт routing key и AMQP `type`.
AI-сервис получает команды из RabbitMQ и публикует ответные сообщения в exchange `generation.results` для backend.

Backend объявляет топологию при подключении: durable direct exchanges, quorum-очереди с `x-delivery-limit: 5` и отдельной DLQ для каждой очереди через `generation.dlx`.
Сообщения передаются как persistent JSON.

Поле `outbox.published_at` хранит время публикации команды и заполняется только после подтверждения от брокера (publisher confirm).
Возврат сообщения брокером (`basic.return`, публикация с `mandatory`) считается ошибкой.

При ошибке публикации backend сохраняет её причину и откладывает повторную отправку команды.
Всего допускается 5 попыток с задержками 5, 10, 20 и 40 секунд.
После пятой ошибки отправка прекращается.
Когда истекает таймаут, backend переводит статус генерации в `failed`.
Записи опубликованных команд и команд с исчерпанным лимитом попыток удаляются по истечении срока хранения `OUTBOX_RETENTION` в `.env` (по умолчанию 7 дней).

Доставка работает по принципу **at-least-once**: сбой между публикацией и записью `published_at` допускает повторную отправку.
Каждый экземпляр backend запускает свой worker без координации, поэтому несколько экземпляров тоже могут отправить одну команду.

При разрыве соединения с брокером оно восстанавливается при очередной публикации или потреблении с увеличением задержки между попытками от 1 до 30 секунд.

### Получение и обработка сообщений RabbitMQ

ID записи outbox передаётся в поле `message_id` сообщения и сохраняется при повторных публикациях.
Тот же ID хранится в поле `message_id` соответствующего результата анализа, коммита или PR.
AI-сервис возвращает его в `correlation_id` ответного сообщения.

Каждый consumer обрабатывает сообщения последовательно с manual ack и `prefetch=10`.
Данные из валидного сообщения сохраняются, только если ресурс существует, находится в `pending` и ID команды совпадает.
Остальные валидные сообщения подтверждаются (`ack`) и игнорируются.
Невалидные сообщения логируются и направляются в DLQ через `nack` с `requeue=false`.
Инфраструктурные ошибки обработки приводят к `nack` с `requeue=true`; после лимита доставок сообщения уходят в DLQ.

Обработка сообщения `analysis.result` зависит от статуса:
- При `done` backend сохраняет `structured_changes` в результате анализа и добавляет команду `commit.request` в outbox в одной транзакции.
- При `failed` backend записывает причину в лог и переводит результат анализа и ожидающий коммит в `failed`.

При обработке `commit.result` со статусом `done` сервер сохраняет `type`, `scope` и `message`.
При `failed` причина записывается в лог, а поля сообщения коммита остаются `NULL`.

При обработке `pull_request.result` со статусом `done` сервер сохраняет заголовок и описание PR.
При `failed` причина записывается в лог, а заголовок и описание остаются `NULL`.

Чтобы результаты анализа, коммиты и PR не застревали в статусе `pending`, worker таймаутов переводит их в `failed` по истечении таймаута.
Проверка выполняется каждые 30 секунд.
Длительность таймаута задаётся переменной окружения `GENERATION_TIMEOUT` в `.env` (по умолчанию 5 минут).

- Для результата анализа отсчёт начинается с создания записи и включает ожидание публикации и выполнение анализа.
- Для коммита отсчёт начинается с публикации текущей команды `commit.request`, а пока команда не опубликована, с её записи в outbox.
- Для PR отсчёт начинается с перехода в `pending` при первом или повторном запуске и включает ожидание публикации.

При таймауте результата анализа ожидающий коммит тоже переходит в `failed`.
Если ответное сообщение приходит после перехода в `failed`, backend игнорирует его.
Удаление ветки или workspace каскадно удаляет изменения, результаты анализа, коммиты и PR.
Ни удаление, ни таймаут не отменяют команды в outbox и RabbitMQ: генерация может выполниться, но её результат будет проигнорирован.

## Разработка

### Локальный запуск

Скопируйте файл окружения:
```bash
cp .env.local.example .env
```

Запустите сервер:
```bash
go run ./cmd/server
```

### Запуск через Docker Compose

Скопируйте файл окружения:
```bash
cp .env.docker.example .env
```

Запустите сервисы:
```bash
docker compose up --build
```

### Заглушка AI-сервиса

`cmd/ai-stub` заменяет AI-сервис при локальной разработке.
Получает `analysis.request`, `commit.request` и `pull_request.request` из RabbitMQ и отправляет соответствующие сообщения `analysis.result`, `commit.result` и `pull_request.result` со статусом `done` или `failed`.
Заглушка подключается к RabbitMQ на `localhost`.
Порт и учётные данные берутся из окружения и `.env`.
Запустите в отдельном терминале:
```bash
go run ./cmd/ai-stub
```

Флаги:
- `-result`: режим результата (`done`, `failed` или `random`), по умолчанию `random`.
- `-success-rate`: вероятность успеха в режиме `random`, по умолчанию `0.8`.
- `-delay`: задержка перед отправкой результата, по умолчанию `1s`.
- `-seed`: начальное значение генератора случайных чисел для воспроизводимых результатов, по умолчанию используется текущее время.

### Доступ

Swagger UI: http://localhost:8080/swagger/index.html
